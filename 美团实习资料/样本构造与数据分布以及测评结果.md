#### ① 条件查找

```text
你是一个合成数据生成器。请根据提供的菜单（Menu）生成一个"条件查找"类的点餐训练样本。

**本次任务特定要求**:
请生成一个 **{selected_type}** 类型的查询。
请**不要**总是生成关于"辣"的查询，多尝试其他口味（酸、甜、咸、清淡等）或其他属性。

**任务步骤**:
1. **生成用户Query**: 模拟用户根据特定条件查找菜品的请求。Query必须是针对该菜单中存在的菜品（或不存在但符合逻辑的情况）。
2. **生成工具调用**: 构建 `recommend_dish` 工具调用，`subIntent` 必须为 "菜品查找"，`recommendType` 必须为"条件查找"。
3. **匹配菜品列表**: 从提供的菜单中，找出所有符合 Query 条件的菜品名称。
4. **多样性**: 不要模仿参考Query的具体内容，只参考其口语化表达风格。

**输入菜单**:
{menu_str}

**参考Query风格（仅供参考句式）**:
{examples_str}

**输出格式**:
请直接返回一个JSON对象（不要Markdown代码块），包含以下字段:
- `query`: string
- `tool_call`: object（包含 name, parameters）
- `dish_list`: list[string]（符合条件的菜品名称列表）

**Tool Definition**:
{{
  "name": "recommend_dish",
  "parameters": {{
    "subIntent": "菜品查找",
    "queryUnderstanding": "完整复述用户需求",
    "recommendType": "条件查找",
    "conditions": "具体筛选条件（如'素菜'，'酸甜口'，'牛肉'）",
    "dishNames": []
  }}
}}
注意: dishNames 字段请始终返回空列表 [], 除非是完全匹配的明确菜名查找。

**示例**:
Input Menu: ["红烧肉", "炒青菜", "米饭"]
Output:
{{
  "query": "来份红烧肉",
  "tool_call": {{
    "name": "recommend_dish",
    "parameters": {{
      "subIntent": "菜品查找",
      "queryUnderstanding": "推荐红烧肉",
      "recommendType": "条件查找",
      "conditions": "红烧肉",
      "dishNames": []
    }}
  }},
  "dish_list": ["红烧肉"]
}}
```

#### ⑤ 菜品推荐澄清

```text
你是一个专门生成餐饮点餐用户语料的专家。
请生成 100 条用户想要 菜品推荐 但**表述模糊、缺乏具体筛选条件**的 Query（查询语句）。

1. **不能**包含具体菜名（如"宫保鸡丁"）。
2. **不能**包含具体口味（如"辣的"、"酸的"、"清淡的"）。
3. **不能**包含具体做法（如"红烧"、"清蒸"）。
4. **不能**包含具体食材（如"牛肉"、"土豆"）。
5. **不能**包含具体种类（如"荤菜"、"素菜"、"主食"）。
6. **不能**包含特定标签（如"招牌菜"、"热销菜"、"新品"、"网友推荐"）。
7. **必须**是用户对服务员说的口语化表达。

**参考示例: **
- 疑问类:
  - "你能帮我推荐几个菜吗？"

  - "今天有什么好吃的？"（注: 虽有"好吃的"但依然模糊）
- 陈述/命令类:
  - "上几个菜"
  - "来几个菜"
  - "推荐几个菜"
  - "上菜"
  - "给我来几个菜"
  - "随便来点"
  - "看看上吧"
  - "整点吃的"
  - "饿了，快点上菜"

**要求: **
- 句式多样化，包括疑问句、陈述句、感叹句、短语等。
- 覆盖不同客群的语气（礼貌、随意、急切、方言风等）。
- 仅返回生成的 Query 列表，每行一个。
- 不要带序号。
```

#### ⑦ 拒绝

```text
你是一个合成数据生成器。请基于上一轮的点餐推荐，生成一个用户"拒绝"或"修改条件"的后续对话样本。

**上一轮对话背景**:
- 用户Query: "{prev_query}"
- 系统理解条件: "{prev_conditions}"
- 系统推荐菜品: [{recommended_dishes_str}]

**任务要求**:
生成用户的下一句Query，表达对推荐结果的不满或进一步筛选，并生成对应的助手工具调用。

**用户Query类型（请随机选择一种生成）**:
1. **全部拒绝/换一批**: 如"都不喜欢，换一批"、"有别的吗"。
2. **部分拒绝**: 如"不要{recommended_dishes[0]}"、"除了{recommended_dishes[-1]}其他的都要"。
3. **增加/修改条件**: 如"太辣了，要清淡点的"、"有更便宜的吗"、"不想吃这种做法的"。

**Assistant响应要求**:
- `queryUnderstanding`: 必须综合上一轮的意图 + 本轮用户的拒绝/修改意图。例如: "上一轮条件，但不要[被拒绝的菜]" 或 "上一轮条件，且要是[新条件]"。
- `conditions`: 更新后的筛选条件，如果是单纯拒绝某些菜，条件应包含排除逻辑（如"牛肉菜品，不含xx, yy"）。

**输出格式**:
请直接返回一个JSON对象，包含以下字段:
- `prev_turn`: object（原始的上一轮数据）
- `user_refusal_query`: string（用户的拒绝/修改指令）
- `assistant_tool_call`: object（新的工具调用）
```

```text

生成要求:
1. **多样性**: 咨询角度请从以下维度中随机选择两个不同维度: 口味（辣度/甜度/咸淡）、食材（新鲜度/具体配料/过敏源）、价格（性价比/具体价格）、分量（够几个人吃/大小）…
2. **口语化**: 用户的提问（user_q1, user_q2）必须口语化，**严禁**在提问中重复出现完整菜名，请使用"这个"、"它"、"这道菜"、"那"等代词，或者省略主语，因为上下文（已知）。
3. **准确性**:
   - `q1_understanding` 和 `q2_understanding` 是系统对用户意图的标准化理解，**必须**包含完整的菜品名称 `{dish_name}`，并且**完整复述**用户的具体问题。
     - 错误示例: "{dish_name}口味咨询"、"{dish_name}分量咨询"
     - 正确示例: "{dish_name}辣不辣"、"{dish_name}一份够几个人吃"、"{dish_name}是不是用新鲜活虾做的"
   - `tool_a1` 是工具查询后的回复，内容要具体、真实感强，不要只说"好"或"不好"，要给出具体理由或数据（如"月售1000+"、"选用澳洲进口牛肉"等）。

请生成以下5个字段:
1. `user_q1`: 用户针对 `{dish_name}` 提出的第一个问题（代词指代）。
2. `q1_understanding`: 系统对 `user_q1` 的意图理解（格式:"{dish_name}" + 具体问题复述）。
3. `tool_a1`: 针对 `user_q1` 的工具回复（模拟真实的菜品详情信息）。
4. `user_q2`: 用户基于上文或新的维度的追问（代词指代）。
5. `q2_understanding`: 系统对 `user_q2` 的意图理解（格式: "{dish_name}" + 具体问题复述）。

请直接返回标准的 JSON 格式数据，不要包含 Markdown 格式（如 ```json ... ```)。
{{
  "user_q1": "...",
  "q1_understanding": "...",
  "tool_a1": "...",
  "user_q2": "...",
  "q2_understanding": "..."
}}
```
