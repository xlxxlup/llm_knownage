# 美团实习项目话术 —— AI服务员Agent工具链建设

> 对应简历「AI服务员Agent工具链建设」这一条。只覆盖工具链部分（菜品推荐/菜品咨询的检索链路设计），
> 实体抽取/匹配微调/刷数提效在另外的话术里展开。
> 引用块（>）里是面试话术提示，不是正文。

## 一、项目背景：AI服务员是什么

美团到餐场景的智能点餐对话 Agent。用户在门店点餐页和 AI 服务员对话，整体架构是：

**主 Agent（qwen3-8b，微调过的小模型）做意图识别 + 槽位抽取（原生 Function Calling）→ 按意图路由到工具 → 工具内部检索菜品知识库、调小模型生成 → SSE 流式输出（文本 + 菜品卡片）**。

六个意图：菜品推荐、菜品组合推荐、菜品信息咨询、购物车操作、个性化服务（忌口/备注）、闲聊。命中前三个才进菜品检索链路，后面三个不走模型检索（固定文案/闲聊）。

我负责其中**菜品推荐、菜品咨询两个工具及其检索链路**，核心是把菜品-评论关联的能力沉淀成 Agent 统一的检索底座。

> 开场先讲清 Agent 分工：主 Agent 只做理解和路由（小模型，快、便宜），重活下放到工具里。
> 面试官问"为什么不让主 Agent 直接推荐"时的标准答案：①菜单有时效性，直接生成会幻觉出不存在的菜；②工具能返回结构化菜品卡片（价格/加购），纯文本做不到；③检索链路可解释、可优化，哪一步坏了换哪一步。

## 二、两个工具的链路总览

### 菜品推荐（发现型）

```
用户："推荐几个不辣的荤菜，50块以内"
  ↓ 主Agent Function Calling 抽槽位
{subIntent:菜品查找, conditions:{种类:荤菜, 口味:不辣, 价格:≤50}, recommendType:条件查找}
  ↓ 检索漏斗（见第三节）
硬约束过滤(种类/口味/价格/菜名) → 双塔召回(食材实体) → 软语义+业务分融合 → Top菜品
  ↓ 富字段 + 关联评论注入提示词
小模型生成 reply + 每道菜的推荐理由（引用真实食客原声）
  ↓ SSE：先菜品卡片，后流式文本
```

### 菜品咨询（答疑型）

```
用户："小炒黄牛肉辣不辣"、"A和B哪个量大"
  ↓ 主Agent抽 dishNames（可能是俗称/口语）
实体-菜关联定位标准菜 → 富字段 + 关联评论注入 → 生成客观介绍/多菜对比
```

两者的区别要讲清：**推荐是发现型链路**（召回+排序+说服性输出，评论当背书），**咨询是答疑型链路**（定位+信息性输出，回答价格/口味/做法疑问）。关联评论在两个工具里的用法是一样的——注入提示词当「网友评论」列，这是"统一检索底座"的含义。

## 三、核心设计：菜品查找的检索漏斗（重点讲这段）

### 3.1 前提：菜品侧标签是预建好的

每道菜提前建好结构化标签：**种类**（荤菜/素菜/主食/汤/饮品）、**口味**（辣/不辣/酸甜/清淡…可多值）、**食材**、**适宜人群**（小孩/孕妇）、**价格**、**业务标签**（招牌/热销/网友推荐/新品）+ 销量。这一步是离线标签体系做的事，检索层只消费。

### 3.2 漏斗：硬约束过滤（Filter）→ 双塔召回（Recall）→ 软语义（Rank/Fallback）

**第一步：条件解析（LLM 槽位化，最关键的一步）**

主 Agent 的 Function Calling 不只输出 conditions 字符串，而是直接输出**结构化槽位**：种类/口味/食材/价格区间/适宜人群，槽位取值对齐标签词表（受控词表）。「想吃点不辣的」「清淡点」「别太油」这类表述差异，**在解析层就被归一化**了（不辣/清淡→口味=清淡）。

> 为什么不让检索层自己解析：LLM 做自然语言→结构化是最强的（同义/否定/口语都处理得掉），
> 检索层只做匹配，职责分离。这一步做完，后面每层都变简单。

**第二步：硬约束过滤——只收「无歧义」的枚举/数值约束（种类、口味、价格、菜名）**

这四类对预建标签做集合成员/区间过滤，硬匹配的对象是**归一化后的槽位值而不是用户原文**，所以不存在"表述不同匹配不上"（表述问题已在解析层解决）。三类约束只有符号系统能精确处理：

- **否定**：「不辣」包含"辣"，字符匹配会召回所有辣菜，符号匹配 口味∈{清淡,微辣} 才是对的
- **数值**：「50 以内」要区间比较，文本相似度算不了
- **精确菜名**：「宫保鸡丁」要精确命中，embedding 可能召回语义相近的另一道菜

**注意食材故意不进这一层**——因为食材标签有**主体歧义**：「牛肉粉」的 ingredients 里也含牛肉（它是配料），硬过滤 `食材=牛肉` 会把牛肉粉照样滤进来。主体问题标签系统解决不了，交给下一步。

**第三步：双塔召回——食材类实体走「实体→菜」微调 Embedding**

用户提到具体食材/实体（牛肉）时，实体塔算一次 query 向量，菜品塔的离线索引里 cosine 取 top-K。这就是双塔微调时负例（同食材不同主体：牛肉 vs 牛肉粉）学到的**主体边界能力**在检索层的消费点——同样的数据、同样的模型，离线做评论-菜匹配，线上做食材-菜召回，一次微调两用。无实体约束（纯模糊推荐）时这一路换成标签分组召回（招牌/热销/网友推荐）。

**第四步：软语义——主观属性排序，召回不足时升级为扩展器**

「适合小孩吃」「健康减脂」「看着好看」不可枚举，与菜品标签组合/检索文本算语义相似度，作为**排序权重**（此时候选集已由 filter+双塔确定）。当 **filter+双塔召回为空或数量过少**时，软语义升级为**召回扩展器**：放宽最次要硬约束 + 在全菜单上做语义召回补齐候选，再不足走热销兜底。

**第五步：融合排序 + 选菜模型**

候选内按「双塔相似度 + 软语义相似度 + 标签匹配度 + 业务分（销量/招牌）」加权，再过一步小模型选菜排序（选 1-3 道、排序、输出 match 是/否——match 决定下游话术：匹配就说"为您精选"，不匹配就老实说"先为您挑了几道人气菜"，**兜底绝不能把不满足需求的菜说成满足**，这是话术红线）。

### 3.3 选型对比（面试高频追问，务必背熟）

**为什么不用字符级 Jaccard 做主匹配？**
否定失效（不辣含辣）、无数值语义、无同义泛化（下饭/管饱→主食）。Jaccard 只配当**过滤后候选的辅助重排信号**（标签集合上的轻量相关度），做主匹配上限很低。

**为什么不上 ES？**
ES 解决的是**规模问题**（万店统一检索服务、多租户、terms/range filter + 分词菜名 + 同义词词库），不解决语义问题。单店菜单就百道菜，进程内做标签过滤是微秒级的事。到平台级再上——届时漏斗形状不变：硬约束换成 ES 的 terms/range filter，语义换成向量库 ANN。**架构分层先想清楚，组件是可替换的**。

**为什么 Embedding 不能包打天下？**
通用 embedding 有两个失败模式：**精确约束会漂**（查「50 以内」算不出数值、「宫保鸡丁」可能召回相近菜）和**主体边界会漂**（查「牛肉」召回「牛肉粉」，同食材不同主体）。所以这套架构里有两个 embedding、各管一段：

- **双塔（实体→菜）**：管食材召回，必须微调——负例专门构造「同食材不同主体」「粒度不符」，主体边界是训练出来的，通用模型学不到（见第四节）
- **软语义（属性↔菜品文本）**：管主观属性排序/兜底召回，通用 embedding 基本够用（它只做排序信号不做精确匹配，漂一点无害）

这是我在菜品-评论关联项目里实测踩过的坑：同一个「牛肉」，硬标签和通用 embedding 都会把牛肉粉带进来，只有配对微调过的双塔拦得住。

> 一句话总结（面试金句）：**解析交给 LLM；种类/口味/价格/菜名交给标签硬过滤；食材交给微调双塔（主体边界）；
> 说不清的主观属性交给软语义，召回不足时它降级兜底；规模大了才轮到 ES——Jaccard 只配当重排信号。**

## 四、双塔 Embedding 语义召回（线上复用，面试主动讲的亮点）

菜品-评论关联项目里为离线匹配微调的**双塔 Qwen3-Embedding（实体塔/菜品塔）**，在线上工具链里直接复用：

- **菜品塔离线建索引**：全量菜单向量化一次（菜单变更低频，重算便宜）
- **实体塔在线算 query 向量**：主 Agent 抽出实体后，一次前向 + cosine/ANN 取 top-K
- **双路召回**：双塔语义召回 + 招牌/热销/网友推荐标签召回并行，候选合并后进选菜模型

**主体边界 case（简历里故意没写，面试时主动讲）**：

- 实体「牛肉」→ 召回 炒牛肉、红烧牛肉，**不**召回 牛肉粉（牛肉粉的主体是粉，牛肉只是配菜）
- 实体「炒牛肉」→ 只召回 小炒牛肉、招牌炒牛肉，**不**反向泛化到泛「牛肉」类目菜

通用 embedding 学不到这个边界，因为预训练语料里没有这种"粒度+主体"的判别信号。我们的做法是**用"实体-菜"配对样本微调**：正例是可匹配对，负例特意构造两类——同食材不同主体（牛肉 vs 牛肉粉）、粒度不符（炒牛肉 vs 泛牛肉）。这和离线匹配阶段训练双塔是同一套数据和同一套模型，**一次微调、离线在线两用**。

> 追问"双塔为什么不共享编码器"：实体和菜是两种异质文本（短语 vs 名称+属性），
> 独立塔各自学到合适的表示空间，训练目标是配对相似度（对比学习），推理时两侧可以独立缓存/建索引。

## 五、RAG 注入：富字段 + 关联评论

选菜完成后，把 Top 菜品的**富字段表**（名称/规格/价格/口味/食材/做法/销量/标签/网友评论…16 列）注入提示词，让生成模型输出 reply + 每道菜的推荐理由。

**为什么注入关联评论**：没有评论时模型只能复述菜品描述，生成内容"无依据、不可信"；注入真实食客原声后，推荐理由变成"外焦里嫩会爆浆"这种有一手背书的话术，可信度和种草力完全不同。评论选取有三条规则：

1. **情感过滤**：只注正向/中性（关联项目产出的实体级情感标签在这里消费），负评进了 prompt 会污染推荐话术
2. **与查询相关优先**：用户问辣的，优先注提到口味的评论
3. **top-3 封顶**：控制 prompt 长度和噪声，评论多了模型反而抓不住重点

> 追问"为什么不多给几条评论"：一是 prompt 预算（富字段已有 16 列），二是实测 3 条正向高相关的信噪比最好。

## 六、知识库的线上存储与加载（白话版）

> 这一节全是后端存储概念，先用比喻建立直觉，再逐条对应到技术词（括号里），面试时两套说法都要会说。

### 6.0 比喻先行：办公桌、文件柜、档案室

把 AI 服务员想象成一个客服，回答用户关于某家店菜单的问题：

| 比喻 | 技术词 | 特点 |
|---|---|---|
| **档案室** | 数据库（Hive / MySQL） | 存全量资料，最全但取一次慢（Hive 分钟级、MySQL 毫秒级）。只用来"提前备料"，不直接服务用户 |
| **共享文件柜** | Redis，即 **L2 缓存** | 楼里所有客服**共用**的柜子，放"整理好的一页纸"（某店的菜单+评论+向量打包），取一次约 1 毫秒 |
| **办公桌** | 程序自己的内存，即 **L1 缓存** | 伸手就到（微秒级），但只摊得开几份资料 |

- **L1 / L2 = 第一层 / 第二层**：离程序越近越快、容量越小
- AI 服务员部署几十上百个实例（程序拷贝）分摊用户流量，每台机器的"桌面"是各自的，"文件柜"是共享的——我桌面没有的，去文件柜可能拿到**别的机器已经整理好的**，就不用打扰档案室
- 取数流程（术语叫 **cache-aside 旁路缓存**）：要用 → 先查桌面 → 查文件柜 → 最后查档案室，拿到后往上两层各放一份。缓存全丢了也不影响正确性，只是慢一次

### 6.1 先算账：规模与访问模式

- 门店数十万家 × 每店 100+ 菜 ≈ 数千万菜品；每菜几十条评论 ≈ 十亿级评论
- 但**一次会话只 touch 一家店**：用户进店后所有检索都在单店空间内（100+ 菜、几千条评论、100+ 菜品向量）

> 面试金句：**数十万店的规模问题，在店维度的访问模式下退化成了单店 KB 级问题**——按店分片 +
> 懒加载 + 预计算，就不需要把十亿评论放进任何一台在线机器的内存。

### 6.2 四层各自干什么

| 层 | 干什么（白话） |
|---|---|
| **Hive 离线数仓** | "夜间工厂"：每天/每次数据变更，把所有重活干完——算完全部菜的向量、把评论和菜关联好、按情感筛好每道菜的正向 top-N 评论。产出的是"成品"，不是原始数据。**Hive 查一次要几分钟，线上绝对不碰它** |
| **在线数据库（MySQL 类）** | 放 Hive 产出的成品，按门店编号建索引（数据太多，按门店号拆到很多机器很多表上，术语叫分库分表），查一家店毫秒级 |
| **Redis（共享缓存）** | 按店打包的"一页纸"，头部热门店常驻，所有实例共享 |
| **程序内存（各自缓存）** | 活跃店的包，最近用过的留着、最久没用的扔掉（术语叫 LRU 淘汰），每份带保质期 |

"**物化/预计算**"这个词的意思就是：**提前算好结果直接存，线上不算**。比如每道菜注入哪几条评论，是离线定死的固定 top-N，线上只是取。

### 6.3 加载时机：按店懒加载 + 头部预热

既不是"用户进店才从零加载一切"，更不是"程序启动时把几十万店全装内存"（几十万店 × 每店约 1MB ≈ 几百 GB，装不下）：

1. 用户进 A 店 → 查桌面（内存）→ 命中直接用，**整个会话后续每轮对话零加载**
2. 没有 → 查共享文件柜（Redis，约 1 毫秒）
3. 还没有 → 查在线数据库，组装 A 店数据包（第一次约几十毫秒，一次性），回填上面两层
4. 热门店提前"预热"进文件柜；冷门店等第一个进店用户触发加载

### 6.4 资料过期怎么办：保质期（TTL）+ 版本号核对

商家可能刚改了菜单，桌面的资料是旧的。两个机制配合：

- **保质期（TTL，比如 60 秒）**：过期后不能直接信，要核对
- **版本号核对**：核对**不是重新拉全部资料**，而是看一眼"这家店菜单的版本号"（商家每改一次菜，版本号 +1）。桌面资料的版本号和最新的一致 → 没改过，续期接着用；不一致 → 重新拉一份。核对成本 = 读一个数字

### 6.5 Embedding 的存与算（谁离线谁在线）

- **菜品向量**：Hive 里离线批量算好（菜单变更才重算那家店），**按店打包**跟着菜单一起缓存，单店约 100 个
- **整套在线链路不需要向量库/ANN**：单店 100 个向量逐个算相似度（术语：暴力余弦）是微秒级、且是**精确 top-K**；向量库（Milvus/HNSW 那类）是为百万级以上全局库设计的，而业务上**不存在跨店检索**，引入它只增加复杂度和近似误差。这是刻意的技术选型克制——不是不会用，是这个场景用错了工具
- **query 侧向量**：对话发生时算一次（实体塔/条件向量），用户进店时不算任何东西
- **评论不在线算**：注入的评论是离线物化好的固定 top-N（情感筛正向 + 相关性预排），线上只取

### 6.6 容量/性能账（面试主动给数字）

- 单店包估算：100 菜 × ~2KB 菜品信息 + 100 × ~4KB 向量（1024 维）+ 预计算评论 ≈ **< 1MB**
- 每个程序实例按 LRU 保留数千个活跃店 → 单实例几 GB 内存
- 热路径（会话内）全部桌面命中：检索微秒级、零网络；回源只在首次进店和版本变更时发生

## 七、常见追问 Q&A

**Q1：菜单改了怎么生效？**
知识库分层加载（详见第六节）：在线 DB 真相源 + 进程内缓存（TTL + 版本号对账），商家改菜后 bump 该店版本，实例对账到新版本回源重载。菜单是低频变更数据，这套足够；多实例加 Redis L2 防冷启动击穿。

**Q2：conditions 解析错了怎么办？**
三层兜底：①受控词表约束输出空间（解析只能输出词表内的值）；②槽位置信度低时该约束不进硬过滤、转语义残差；③最终还有空结果降级链 + match=否 的诚实话术。

**Q3：菜品咨询里用户说的菜名是俗称/错别字怎么定位？**
候选召回（按菜名/食材）→ 判断类似（俗称/学名/错别字/修饰词容错）→ 全部判否则提示"没找到完全一致的，这些是相关菜品"。注意：**这一步是咨询工具自己的定位模块，不走实体-菜关联**——实体-菜关联是评论世界到菜单的映射，用户直接报菜名走的是菜单侧的模糊定位，两条链路别混。

**Q4：为什么推荐理由单独用一步模型，不和选菜合并？**
输入不同：选菜只需要菜单结构化信息（轻），理由生成需要富字段+评论（重）。分开可以讓选菜在高召回调用量下跑，理由模型专注生成质量；也方便单独迭代话术。

**Q5：线上时延怎么控制？**
主 Agent 一次 function calling（小模型）+ 工具内两步小模型调用，检索层全部进程内缓存命中（微秒级），embedding 只有一次 query 前向。端到端首字延迟主要由模型调用决定，所以每一步都用"最小够用"的模型。
