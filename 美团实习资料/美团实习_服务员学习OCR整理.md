## 智能点餐 AI 服务员


### 一、业务背景

- 智能点餐 AI 服务员是一个 C 端的点餐助手。当消费者去到一家不熟悉的餐厅，不知道吃什么，不知道点什么的时候，我们的 AI 服务员能够根据用户的需求推荐合适的菜品和套餐，从而提高用户的点餐效率以及降低决策成本。

### 二、项目功能

- 中控 Agent 对用户query进行理解，根据用户意图输出需要调用的工具以及参数，并且根据工具的调用结果进行下一步决策
- 菜品推荐：为用户推荐合适的菜品，是菜品粒度的推荐。
- 菜品组合推荐：为用户推荐一个合适的套餐，是套餐粒度的推荐。
- 菜品信息咨询：例如“这个菜是怎么做的？”，“这个菜的主材有什么？”
- 点餐操作：例如“购物车加菜、更换菜、删除菜”
- 个性化服务：记录用户的忌口说明、口味偏好以及其他的个性化偏好。
- 闲聊模块：负责非核心场景的问答

### 三、核心难点

- 多意图复合场景下的语义边界判定以及任务规划
- 多轮对话里的指代消解
- 多轮对话跨轮槽位参数继承

### 四、架构迭代路径


#### 1、BERT意图分类

- BERT 擅长文本分类，但在对话系统中，它只是一个“分类器”，而不是“大脑”。
- 规则硬编码，单意图分发器，多轮对话无状态、无全局规划能力。不支持多意图、没有上下文能力、扩展性差

#### 2、多模型协作

- 主Agent调用GPT-4o-mini接口路由意图；组品大模型做套餐生成；GPT-4.1做菜品问询和闲聊；时延高，多模型割裂，上下文不共享；成本不可控

#### 3、微调小模型 + ReAct范式

- 把问题从「单一分类」升级为「任务规划」，采用 ReAct范式（思考 -> 行动 -> 观察 -> 循环），中控Agent负责意图理解、统一决策，Tool做执行。主Agent是Planner，Tool是Executor。
- 为了降低时延并且保证效果，微调Qwen3-8B模型进行意图理解、意图澄清、参数槽位填充和Tools选择，结合工具执行结果进行多轮对话

### 五、具体流程

- 用户请求 -> 中控Agent分析规划 -> 路由意图到Tool执行 -> 中控Agent汇总执行结果并输出
  - 中控 Agent 根据用户的query、对话上下文进行意图识别、意图澄清、参数槽位填充和Tools的选择。输入为system_prompt、工具定义和Schema、对话上下文、用户Memory和当前用户输入。
    - **Reasoning：**中控Agent 根据用户的query、对话上下文进行意图识别、意图澄清、参数槽位填充等
    - **Action：**如果槽位缺失，则进行意图澄清；槽位完整则输出tool调用结构体
    - **Observation：**工具执行结果作为上下文进行总结，转换为自然语言
  - Tool 根据输出参数执行workflow逻辑

### 七、模型优化

- SFT建立基础的工具调用能力，DPO修正参数提取的偏差，GRPO通过探索式强化进一步解决难样本，提升pass@1指标，模型一次就能生成出正确答案

#### 1. SFT：建立基础的工具调用能力


**a. 数据构造**

- 约5w条数据，来源分为线上真实数据与LLM合成数据（单轮对话为线上真实数据+外包标注、多轮对话场景通过GPT-4o按照模板分场景构造）
- **轮次分布：**1轮 38%、2轮 41%、3轮 14%、4轮+ 7%
- **工具分布：**菜品推荐 40%、组合推荐 20%、菜品信息咨询 20%、闲聊+点餐操作+个性化 20%
- **覆盖核心场景：**单轮意图、槽位缺失澄清（错误工具调用严重影响用户的体验，澄清十分重要）、多轮对话指代关系以及菜名省略、跨轮参数继承、反悔修改、前后矛盾、多意图拆解、意图边界难样本

**b. 训练**

- **基座：**Qwen3-8B（微调时延和成本远低于未微调大模型、指令遵循能力强）
- 全参微调，32张H910-64G
- 对比过qwen3-8b、deepseek-v3-friday、gemini-3-pro-preview、gpt-4.1、longcat-8B-chat、longcat-sales-8B、qwen3-8b-sft（准确率高、时延低）
- Qwen3 8B 部署在 H20 2 张卡上，平均耗时 847.3ms，TP 90 1,061.4ms，平均输入 token 数6436，平均输出 token 数77.13，RPM为300

#### 2. DPO：修正参数提取的偏差


**a. 数据构造**

- **负样本来源：**真实线上数据的badcase、针对SFT模型已知的错误构造典型的负样本
- **构建正负样本对：**每个负样本对应一个人工标注或者GPT-4o修正的正确输出作为正样本，构成（prompt，chosen，rejected）三元组，最终DPO数据集大约3000个pair，重点覆盖参数提取错误和意图边界混淆两类问题

#### 3. GRPO：聚焦多意图、意图重叠、指代消解等难样本


**a. 数据构造**

- 约5000条数据，为SFT数据的分层采样，聚焦于菜品推荐、菜品组合推荐、菜品信息咨询等核心意图以及指代消解场景、澄清场景

**b. 奖励函数设计**

- **类型判断：**该澄清却调用工具 / 该调用工具却澄清，直接 -5.0 重罚
- **澄清场景：**命中标准话术 +3.0，合理非标准话术 +1.0
- **工具调用：**工具合法 -> Schema 合规 -> 工具名匹配 -> 按参数逐项评分（核心参数错误重罚） -> 语义类参数用 GPT-4o 判断是否符合预期
- **奖励函数具体逻辑**（rule-base + model-base）

#### 4. 评测指标

- **总体准确率：**所有样本预测正确的个数/总样本数
- **工具调用准确率：**工具名正确的个数/总样本数
- **意图澄清召回率：**需要澄清并且模型主动意图澄清的个数/所有需要意图澄清的样本个数

#### 5、效果提升

- 准确率从 SFT 基线的约88%，经过DPO提升到92%，再经过GRPO提升到96%。
- 意图澄清召回率达到100%，多意图场景的准确率有明显提升

### 八、记忆模块（分层记忆架构）

- **短期记忆（Redis + 小模型压缩）**
  - Redis 键值对存储当前用户会话 session 内容，包含就餐人数、用户忌口、已点菜品、用户备注等信息，每轮对话结束都会进行更新
  - 当对话轮数超过阈值（如 10 轮）或 Token 数接近窗口上限时，触发压缩
    - 调用小模型进行内容压缩，保留关键信息
- **长期记忆（MySQL + ES）**
  - 将用户口味、忌口、历史订单信息等“硬事实”存储到关系型数据库MySQL作为元数据
    - 数据不会删除，只会更新
  - 将用户的历史对话摘要embedding化存储在向量数据库ES中，既可以向量检索也可以关键词检索
    - 如果存储内容过多会按照存储时间进行记忆淘汰

### 九、问题引导

- 让大模型根据当前对话生成 3 个用户可能点击的快捷引导问题，帮助用户继续点餐。
- 冷启动阶段从预生产引导问题库中各intent中的问题中随机召回一个问题，随机顺序展示；追问阶段直接展示大模型生成的3个引导问题（根据最近的一轮有效query的对话，保证问题不与已生成的问题完全相同）
- 输入：用户本轮输入、系统本轮回复、系统是否在澄清、当前理解的用户需求、识别出的意图类型；输出：三个引导问题（小于12个字）
- 只对「菜品推荐意图」「菜品组合推荐意图」和「菜品信息咨询意图」生成引导问题
- **模型处于澄清阶段：**根据模型的回复预测用户可能回答
- **模型不处于澄清阶段：**按识别的意图生成不同引导问题
- 约束条件
  - 不能与历史生成的问题重复
  - 不能虚构商家没有的菜品或类目
  - 不能生成下单、加购等操作指令
  - 不能生成纯闲聊或空泛确认（如“好的”“谢谢”）

### 十、存在问题及优化方案


#### 1、参数提取不稳定

- dishNames 和 dinerCount 经常无法被正确提取。它们要么被放到了 conditions 字段里，要么就是直接被模型忽略（丢弃）了，导致输出结果缺失。
- 菜品组合推荐多轮人数遗忘
  - **动态提取：**解析当前模型输出，若包含有效“人数”实体，立即更新并保存。
  - **记忆继承：**若当前模型未输出人数信息，优先回溯并继承会话历史中已缓存的有效人数数值。
  - **兜底检查：**若保存的无有效人数，检测用户在UI层面的交互记录（是否点选过人数选项）。
  - **主动澄清：**若上述链路均未获取到有效人数信息，则触发“反问/澄清”机制，引导用户补充人数信息。

#### 2、意图边界模糊且存在overlap，一句话存在多个相似的意图

- 用户表达“想吃点辣的”，用户明确提到了“菜品的口味”，因此是菜品推荐意图。但如果用户在点完菜后说“宫保鸡丁做辣一点”，则是个性化服务意图
- 用户直接说菜品名，如“宫保鸡丁”，应理解为菜品推荐意图，而不是菜品信息咨询意图。菜品信息咨询意图的问法如：“宫保鸡丁是甜的吗？”、“宫保鸡丁是什么菜系？”、“宫保鸡丁的做法？”等。
- 用户询问具体菜品够几个人份，属于菜品信息咨询意图，而不是菜品组合推荐意图。
- 用户询问“火锅锅底有微辣的吗”，表示“用户想要微辣的火锅锅底”，属于菜品推荐意图，而不是菜品信息咨询意图，菜品信息咨询的问法是“火锅锅底辣不辣”。
- 用户询问“听说你们这儿的菜不错，都有什么选择？”，表示“用户想要菜品推荐”，属于菜品推荐意图，不是闲聊意图。

#### 3、多轮数据质量不佳

- LLM合成的数据语言风格规整，但是真实用户输入很口语化，有省略、有指代，导致模型训练效果不太好
- 在造数据prompt里加入口语化要求，并且混入线上真实数据提升鲁棒性

#### 4、评测体系的建立

- 准确率的定义存在歧义：工具名对就算对，还是所有参数都对才算对?
- 最终定义了严格的全参数匹配准确率，同时分场景统计

### 十一、效果评估


#### 1、不同粒度评估

- **粗粒度：**全链路端到端评估
- **细粒度：**中控Agent效果评估、各工作流效果评估

#### 2、离线/在线评估

- **离线评估：**构建了一个覆盖六大意图、多轮对话场景、边界case的测试集（约1500条），对每条样本评测完整的工具调用链路，包括意图识别、参数提取等是否正确
- **在线评估：**通过AB实验对比核心业务指标，包括模块使用率、平均对话轮次、点餐完成率、订单转化率等。同时持续收集线上的badcase，人工分析错误原因并溯源。

### 十二、异常处理


#### 1、中控Agent发生死循环

- **步数硬限制：**设定 MAX_STEPS = 3，达到上限后，输出由预设模板生成的“抱歉”回复，并触发人工介入信号，让模型重新反思。
- **重复调用检测：**记录工具调用的 (tool_name, tool_params)，如果检测到连续两次完全一致，让模型重新反思。
- **上下文自动压缩：**如果上下文过长，超过一定的阈值，调用小模型进行摘要处理后再喂给模型，防止 Token 溢出导致模型逻辑崩溃。

#### 2、执行异常（例如：下游服务挂了、工具调用失败、模型宕机）

- 工具执行失败或者结果为空，记录该 Case 并进入降级流程
- 单次 LLM 请求设置 15s Deadline。若超时，记录该 Case 并进入降级流程。

### 十三、全链路稳定性监控


监控不应只看结果，更要看 Agent 的“思考过程”


#### 1、ReAct 过程指标

- 记录 Thought、Action、Observation 各部分的 Token 占比。异常高的 Thought 占比通常意味着模型在“胡乱想”。
- 监控“模型推理-工具执行-结果聚合”各阶段耗时
- 统计各工具的成功率与响应时延

#### 2、业务质量监控 (LLM-as-a-Judge)

- **周期评测：**抽样 5% 的线上日志，由一个更高阶的模型（如 GPT-4o）对推荐结果进行打分（维度：相关性、多样性、是否遵循筛选条件）。
- **线上走查：**每日人工抽检线上对话，评测模型质量、收集 badcase

### 十四、Badcase 闭环与持续进化


#### 1、构建“黄金测试集”

- **动作：**筛选 500-1000 条覆盖全场景（单意图、多意图、指代消解、纠错）的标准对话轨迹。
- **应用：**每次模型微调或 Prompt 修改后，必须通过黄金测试集的自动化回归测试，确保新能力上线不导致旧能力退化。

#### 2、自动化 Badcase 收集链路

- **负反馈触发：**用户点击“换一批”、“不感兴趣”或直接输入“推荐得不对”时，系统自动标记该 Session 为 Badcase。
- **逻辑矛盾捕获：**自动筛选出触发了“步数限制”或“重复调用”的 Case，存入待标注池。

#### 3、人工标注与回哺训练

- **SFT/DPO/GRPO 数据沉淀：**收集线上badcase作为负样本，标注人员纠正负样本，将其转化为高质量的训练数据，提升数据集的质量和多样性。

### 十六、可能会问的问题


#### 1、什么时候需要澄清?

- **必填参数缺失：**当识别出的意图需要核心参数（如“菜品组合推荐”必须要有 dinnerCount 就餐人数）但用户未提及，且记忆模块中也无法回溯时，触发澄清。
- **语义过于模糊：**用户表达如“点几个菜”或“随便来点”，缺乏具体的筛选条件（口味、类别、价格）。此时不直接推荐，而是反问用户偏好（如：“请问您今天想吃清淡点还是重口味一点的？”）。
- **高相似意图冲突：**用户的 Query 处于意图识别的边界（如：用户说“火锅锅底辣不辣”，模型在“菜品信息咨询”和“菜品推荐-查找辣锅”之间置信度接近），主 Agent 会主动询问：“您是想了解锅底的成分，还是想让我为您推荐几款辣味锅底？”

#### 2、有对比过先冷启动后再训练，以及直接后训练的效果吗?

- **直接后训练的缺陷：**Base 模型（如 Qwen3-8B）虽然有基础能力，但在没有 SFT 引导时，很难在 RL 阶段自发探索出符合我们业务定义的复杂 JSON Schema（如特定的 tools 结构）。这会导致 Reward 长期为负，模型无法收敛，或者陷入“乱码”状态。
- **先 SFT 后 RL 的优势：**
  - **Pass@1 基础：**SFT 建立了模型的“格式感”，确保模型输出基本符合 JSON 规范和工具定义。
  - **RL 提升上限：**GRPO（后训练）则是在 SFT 已经能跑通的基础上，利用“组内相对奖励”解决 SFT 难以解决的参数提取不稳定和意图边界模糊问题。

#### 3、SFT一般需要多少数据进行训练？GRPO一般需要多少条?

- **SFT 数据量：**通常在 1万到 3万条 左右。需要覆盖 6 大一级意图、10+ 子意图，包含单轮、多轮、指代消解、意图澄清等。通过 LLM 构造（GPT-4.1 生成）和线上真实数据清洗标注相结合，确保模型“见多识广”。
- **GRPO 数据量：**规模通常在 1000 到 5000 条 高质量 Prompt 即可。GRPO 并不需要海量数据，它更看重针对性。专门挑选了 SFT 表现不佳的“易混淆 Case”和“参数提取失败 Case”作为 Prompt，让模型在同一组 Query 下生成多个样本，通过奖励函数强制模型学习正确的决策逻辑。

#### 4、上下文过长会有什么问题，怎么解决?

- **存在的问题**
  - **Token 过长：**每个模型都有最大上下文窗口。一旦超过，最早的对话或系统指令会被挤出，导致模型忘记任务目标。
  - **注意力稀释：**研究表明，模型对 Prompt 开头和结尾的信息敏感，如果上下文太长，中间的信息会被忽略。
  - **幻觉增加：**冗余的 Thought 和 Observation 会干扰推理。模型可能会参考过期的观察结果，导致 Action 逻辑混乱。
  - **成本与延迟：**处理的 Token 越多，推理耗时越久，API 调用费用越高。
- **解决方案**
  - **窗口滚动：**只保留最近 N 轮的对话记录。简单直接，但是会丢失长线信息。如果用户在第 10 轮提到第 1 轮的需求，模型会无能为力。
  - **对话总结：**当对话达到一定长度时，用其他模型对之前的对话进行总结并生成一个摘要。
  - **向量检索记忆：**将历史的对话内容存入向量数据库。当新问题进来时，先去数据库检索相关的“历史片段”，选择性注入上下文。

#### 5、AI服务员可以Skill化吗？具体怎么做?

- 每个工具对应一类能力，都可以将逻辑封装为Skill，和主Agent组成标准的Agent+Skills架构
- 是Agent的一种模块化能力封装单元，用于扩展智能体的能力，使其能够自动化执行特定领域的任务。定义每个Skill的任务说明、规则约束、明确的输入输出等

### 五、存在问题及优化方案


#### 1、生成任务开放性较大，模型训练过程容易出现乱码、复读机，导致训练不稳定?

- **奖励函数被破解：**在 GRPO 训练中，如果奖励函数过于侧重某些字面指标（如提取数字个数、包含关键词），模型会为了“刷分”而反复输出这些高分词汇，导致“复读机”。
- **缺乏 KL 散度约束：**训练过程中新旧策略模型偏差过大，模型陷入了某些不可解释的局部最优空间，表现为输出乱码。
- **SFT 质量不均：**冷启动阶段的训练数据如果包含截断的评论或无意义的字符，模型在蒸馏过程中会放大这些噪声。
- **简单样本缺乏区分度：**对于常规query，模型倾向于生成高度相似的样本，导致正负样本之间的区分度不足，从而导致梯度冲突。采用细粒度的奖励函数量化样本区分度、设置动态阈值过滤分差小于3的样本。
- **困难样本基准缺失：**对于困难query，在模型训练初期，模型生成的rollout质量较差，GRPO的奖励稀疏。对于困难样本通过离线注入deepseek-r1生成的高质量数据，引导模型生成更好的rollout，使模型训练更加稳定。

#### 2、统一模型跷跷板现象，某一维度的效果下降?

- **梯度竞争：**不同维度的任务（如停车指南侧重逻辑与数字，POI 亮点侧重描述与修辞）在训练时产生的梯度方向不一致，导致权重更新时互相抵消。
- **数据分布失衡：**训练集中某一任务的数据量占比过大，导致模型偏向于学习该任务，牺牲了小样本任务。
- **Prompt 混淆：**统一 Prompt 格式后，模型对于不同任务的指令跟随能力受到干扰。

## 面试题


### 1、在 grpo 训练中有没有遇到过 Reward Hacking 问题，是如何解决的?

- **具体问题**
  - 模型发现输出内容只要满足硬性限制即可得到更高的奖励（例如复读机、乱码），相对于那些不符合格式要求的rollout得到的分数更高
- **解决方法**
  - 适当减小学习率，防止模型训练的时候步子迈太大
  - 适当调高KL系数，限制新策略与reference model策略的距离，防止模型过多偏离原策略
  - 根据实际case，在奖励函数中增加相应的限制（by case完善奖励函数），规则和LLM一起组成奖励函数
  - 增加对推理过程的奖励评估，利用LLM来检测输出结果的逻辑和语义

### 2、什么是熵坍塌？怎么解决？

- 熵坍塌指的是，模型在训练几步或几十步之后，输出的概率分布急剧变锐化，模型输出内容单一，GRPO 优势计算都为0。
- 在loss函数中加入熵正则项，鼓励模型保持探索空间
- 增加 clip 上界，以及增加 KL 散度的系数，让模型更新幅度变大
- **rollout 阶段多样性：**增加温度、增加 G，一直 rollout 直到 reward 具有多样性
- 结果奖励太单一，增加过程奖励，对输出的思考步骤进行打分

### 3、如何判断是否需要 RL?

- 就是判断 sft 模型的能力是否到达了上限。
- 从 loss 和结果的角度，train set loss 不再明显下降，下游任务指标趋于稳定
- 比较 pass@1 和 pass@k，如果 pass@k 可以做对，pass@1 做不对，此时需要 RL
- 另一方面根据任务的性质判断，一些没有标准答案的任务，一些需要拒答的任务，比如，医疗，法律，安全；需要多步复杂推理的任务，比如 agentic rl，复杂的数学证明、代码生成，需要模型去“试错”和“探索”。
- 从数据的角度，如果一个任务的数据人工标注困难，但是评估很简单，就可以使用 RL。

### 4、怎么判断一个任务 rl 之前是否需要冷启动

- 问题的关键在于，模型现在的能力是否在“有效搜索空间”内
- 基座模型直接回答垂域问题，它生成的答案中，是否有一定比例是基本正确、符合格式且逻辑通顺的?
- 如果基座模型在垂域指令跟随能力不强，rl 探索全是无效的路径，在 GRPO rollout 过程中 reward 全是0，无法学习到任何知识。

### 5、GRPO rollout 过程 reward 全是 0 如何解决?

- 先排查问题，查看打印训 rollout 过程数据，查看输出是不是生成长度不足被截断、输出是否乱码、输出格式是否有问题，reward 计算逻辑是否正确
- 从 rollout 的角度，增加温度，增加 G，一直 rollout 直到 reward 不全是错的。
- 模型的角度，reward 全是0，说明模型模型能力不行或者部分数据任务难度较大，先进行冷启动
- 算法的角度，采取更细粒度的细化 Reward 设计，避免使用单纯的二值
- 引入额外的 ref 或者历史基线

### 6、为什么做 RL，RL 解决的这些问题为什么 SFT 解决不了？如何判断是“SFT 没训好”还是“SFT这种方法本身到了天花板”?

- **问题1**
  - SFT 的本质是“模仿”，泛化性相较于微调前变差
  - SFT的训练效果达到瓶颈，无法解决一些corner case和hard case
  - SFT 是在拟合人类的数据分布，数据的上限即模型的上限，对于逻辑复杂的任务，高质量 SFT 样本的成本极高；SFT 只能告诉模型“什么是对的”，无法有效地告诉模型“什么是错的”
  - RL 的本质是“探索与对齐”，一些没有标准答案的任务（内容生成）、需要多步复杂推理的任务（数学证明、代码生成），需要模型去“试错”和“探索”。
- **问题2**
  - 从 loss 和结果的角度，train set loss 不再明显下降，且效果无法得到提升
  - 比较 pass 1 和 pass k，如果 pass k 可以做对，pass 1 做不对，此时需要 rl

### 7、最近一年对于 GRPO 的改进有哪些

- **DAPO**
  - 解决熵坍塌、梯度消失、长回答奖励噪声
  - **提高采样上限：**上界调大，鼓励探索；下界保持较小值，保持训练稳定。通过解耦上下界，避免过早陷入局部最优
  - **动态采样：**组内回答全部正确或者全部错误，导致梯度消失，对于输入的样本持续采样，直到组内存在优势差异
  - **token级别策略梯度损失：**GRPO采用sample-level，首先对样本内容做平均，然后对group所有样本做平均，导致长回答对于loss的贡献被稀释；DAPO采用token-level，用总token数做平均，模型会重点关注长回答
  - **长回答奖励噪声：**对模型生成的长回答进行惩罚，而不是施加硬惩罚
  - **去除KL散度约束：**long-COT训练过程中，模型本来就是要在较程度上偏离原始的状态，所以去除用于约束模型更新的KL散度。

### 8、带 think 的 GRPO 和不带 think 的 grpo 有什么区别

- **奖励函数的角度：**带 think 可以设计更丰富的奖励函数，有过程奖励和结果奖励。不带 think 的 grpo 只有结果奖励。带think 的 GRPO 更容易训练
- **探索空间的角度：**带 think 的文本更长，探索空间更大，rollout 的样本多样更新大，不带 think 的探索空间比较小，容易输出结果一样，优势函数计算为 0，梯度变成 0
- **任务的角度：**带 think 的 GRPO 更适合，数学推理、代码生成、复杂逻辑谜题、多步规划等有客观正确答案且过程比较复杂。不带 think 的 GRPO 更适合通用对话、角色扮演、写作辅助、信息抽取等任务。
- **算力的角度：**带think的GRPO的token长需要花费更多费用，不带think的GRPO便宜。

### 10、LoRA的AB矩阵参数为什么这么初始化?

- ΔW = AB，矩阵A降维，矩阵B升维
- 随机初始化降维矩阵A引入高斯噪声，促进模型在低维空间探索新特征方向，避免微调陷入局部最优
- 升维矩阵B初始化为零保证训练起始阶段附加层不改变原模型输出，维持预训练权重稳定性
- 如果矩阵A与B均零初始化则梯度消失无法学习
- 如果均随机初始化则初始扰动过大可能破坏预训练特征表达

### 12、多轮对话时用户和模型的对话上下文很长怎么办?

- **上下文压缩与精简 (Compression)**
  - **滑动窗口 (Sliding Window)：**仅保留最近的 N 轮对话，丢弃最早的信息。这是最简单的方法，但会导致模型“失忆”，忘记最初的指令。
  - **总结压缩 (Summarization)：**当对话达到一定长度时，调用一个轻量级模型将之前的对话摘要成一段话，作为背景信息保留，随后清空原始历史。
  - **关键信息提取：**利用启发式规则或模型，仅保留对话中的关键实体、事实和当前任务的核心指令，剔除语气助词和冗余信息。

### 13、幻觉问题怎么解决?

- **外部知识增强 (RAG)**
  - **检索增强生成 (Retrieval-Augmented Generation)：**在模型回答前，先在向量数据库中检索相关的实时、准确文档，并将其作为上下文（Context）输入给模型。
- **推理阶段策略 (Inference-Time)**
  - **思维链 (Chain of Thought, CoT)：**引导模型写出中间推理步骤。研究表明，让模型“先思考再回答”能显著减少逻辑层面的幻觉。
  - **Self-Consistency（自洽性检查）：**让模型对同一个问题生成多个不同的采样结果，通过投票或对比，选择出现频率最高、逻辑最一致的答案。
  - **降低采样随机性：**在需要事实准确性的场景（如医疗、法律），降低 temperature（接近 0）和 top_p 参数，减少模型为了“多样性”而产生的胡编乱造。
  - **System Prompt 约束：**在系统提示词中明确告知模型：“如果不知道答案，直接回答不知道，不要试图编造。”
- **训练与对齐 (Training & Alignment)**
  - **RLHF/DPO (强化学习与偏好对齐)：**在强化学习中，特意加入关于“真实性”的偏好引导。如果模型拒绝回答未知事实，给予正向奖励；如果编造事实，则给予惩罚。
- **多模型验证与纠错 (Verification)**
  - **多智能体协作 (Multi-Agent)：**引入一个专门负责“事实核查”的模型（Critique Agent），对主模型生成的草案进行审查，指出潜在的幻觉点并要求主模型重新生成。
  - **结构化输出约束：**强制模型输出 JSON 或特定格式，并结合代码（如 Python 解析器）进行逻辑校验，防止模型在格式转换中产生幻觉。
